# Internationalization

Yuli Ledger is an **English-native project**. Simplified Chinese is a first-class **locale**, not the language of identifiers or source strings.

## What stays English

| Surface | Language |
|---------|----------|
| Repository, docs, commit messages | English |
| Code identifiers, file names, Tauri command names | English |
| Entry kind ids (`income`, `expense`, `repayment`, `prepayment`, `transfer`) | English tokens |
| Preset ids and i18n keys | English tokens |
| Source UI catalog | English |

Do not name kinds `shouru` / `zhichu`. Do not translate folder names under `src/`.

## What is translated

The UI catalog: button labels, screen titles, validation messages, kind **display** names, preset **display** names, settings copy.

Locale id for Simplified Chinese: **`zh-Hans`**.

English catalog locale id: **`en`**. English is the **source**; `zh-Hans` is a translation of `en`, not a second original.

## Runtime

- User can switch UI language in settings. Persist the choice as `LedgerSettings.uiLanguage` (`en` or `zh-Hans`). When it is null, follow Windows UI language if that is `en` or `zh-Hans`, otherwise `en`.
- Color scheme is independent (`colorScheme` in [ui.md](ui.md) / [domain-model.md](domain-model.md)).
- Switching language does not rewrite user data.
- Formatting of numbers, dates, and times follows the **active UI locale** (and still uses local timezone for `occurredAt` display as in [domain-model.md](domain-model.md)).

## Keys

Use stable dotted keys, for example:

- `kind.income`, `kind.expense`, `kind.repayment`, `kind.prepayment`, `kind.transfer`
- `preset.account.default`
- `preset.category.transport`, `preset.category.transport.bus` (seed only: [preset-categories.md](preset-categories.md))
- `preset.category.transfer`, `preset.category.transfer.fee`
- `report.week`, `report.month`, `report.year`, `report.custom`
- `report.side.expense`, `report.side.income`
- `error.amountInvalid`
- `error.transferSameAccount`, `error.transferDestExceedsSource`

The key is the API. The English sentence is the default value in the `en` catalog. Missing `zh-Hans` entries must **fall back to English**, never to the raw key if an English string exists.

## User-generated text (not i18n)

Account names the user types, category names they create or rename, tags, **account notes**, and entry notes are stored exactly and shown as stored. They do not pass through catalogs.

## Preset accounts and categories

Recommended pattern (required for v1 presets):

- Store a stable `id` and `presetKey` (the i18n key).
- Display name = translated string for `presetKey` **until the user renames**.
- On rename, keep `presetKey` for identity if useful, but **display the user name thereafter** (a `nameOverride` or simply writing `name` and treating non-null user name as override). Do not keep showing Chinese/English from catalogs after a rename.

Do **not** seed two rows per preset (one English, one Chinese). Do **not** store only a Chinese name in the database as the source.

User-created categories have `presetKey = null` and a single `name`.

## Kind labels

Kind **ids** stay English tokens (`income`, `transfer`, …). Kind **labels** always go through `kind.*` keys. Reports and pickers use the translated label; exported or debug views may show the id.

## Quantity and grammar

Prefer message patterns that do not require heavy plural engines for v1 (personal finance UI is mostly labels and forms). If a plural is needed, use the i18n library’s plural rules for `en` and `zh-Hans` rather than concatenating strings.

## Implementation

Catalogs live in `src/i18n/` (`en.ts` source, `zh-Hans.ts` translation). Runtime uses i18next; missing `zh-Hans` keys fall back to English.
